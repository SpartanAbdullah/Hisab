# Hisaab 2.0 Privacy & Data Safety Inventory

Prepared for future Android and Google Play Store readiness. This inventory is based on inspection of the current React/Vite codebase, Supabase data access layer, local storage usage, export/import utilities, and app settings screens.

Last reviewed: September 5, 2026 (launch alignment: every migration applied to production 2026-09-03/04; push/FCM live; Sentry in the release build; analytics absent from this build; CAMERA permission; opt-in phone discovery; investment + kameti records; D1 deletion refusals). Every claim below cites the source migration/file it was verified against. **The authoritative Play Console answer table lives in `docs/play-store-data-safety.md` §1** — this file is the evidence trail behind it; §7 below mirrors it and must not drift.

## 1a. New tables and flows added 2026-09-02

Every migration in this section (and every other file in `supabase/tests/apply-order.txt`) was **applied to production in the 2026-09-03/04 batches** — there is no migration runner in this repo (see `CLAUDE.md`), the founder ran them in Supabase Studio and the 546-assertion DB suite passes against the same order in CI. All of these flows are live. Client code for each still degrades safely against an un-migrated database (typed "unavailable" errors, not corruption or a crash), which matters only for a future staging project.

| Table / flow | Purpose | Fields | Who can read (RLS) | Retention / pruning | Deletion behaviour | User-facing control |
|---|---|---|---|---|---|---|
| `public.blocks` | One-sided, silent block of another user | `blocker_id`, `blocked_id`, `reason` (≤500 chars, trimmed), `created_at` | **Only the blocker** — no SELECT policy names `blocked_id` at all, so the blocked party can never read, count, or infer a row about themselves | No pruning; a block persists until unblocked | `ON DELETE CASCADE` on both `blocker_id` and `blocked_id` — the row is deleted outright if either account is deleted | Block / Unblock (`supabase.from('blocks').insert/delete`); a "Blocked people" list with unblock is in Settings (`src/pages/SettingsPage.tsx`, audit M17; `docs/trust-and-safety.md` §4.3) |
| `public.reports` | User-to-user abuse/harassment report to the operator | `reporter_id`, `reported_id` (both `ON DELETE SET NULL`), `context_type`, `context_id`, `reason` (≤128), `details` (≤2000), `created_at`, `reviewed_at` | **Nobody via the client** — INSERT-only, zero SELECT policy; only Supabase Studio / `service_role` can read the queue | No pruning defined; capped at 20 inserts/reporter/rolling day (`REPORT_RATE_LIMITED`) | `ON DELETE SET NULL` on both FKs — the report row survives account deletion by design, with the deleted party's id nulled, so a reported user cannot erase the operator's only record by deleting their account | Report action (INSERT-only, optimistic "Report sent" — the client cannot read it back). No operator console; queue is worked by hand in Studio (`docs/trust-and-safety.md` §3) |
| `public.group_guest_identities` | Lets a real person later claim a "guest" (no-account) group seat by phone match | `member_id` (PK, → `group_members`), `group_id`, `phone_hashes TEXT[]` (SHA-256, unsalted — protected by deny-all RLS rather than a secret), `created_by`, `created_at` | **Nobody via the client, at all** — `USING (false) WITH CHECK (false)`, table grant revoked from `anon`/`authenticated`; only the `add_group_guest` write path and the `join_group_by_code` claim-lookup read it | No pruning; row is deleted the moment the seat is claimed (`join_group_by_code`) or the guest is removed | `ON DELETE CASCADE` from both `group_members` and `split_groups` — deleting the guest seat or the group removes it; `created_by ON DELETE SET NULL` if the adding member's account is later deleted | The member who typed the guest's phone can remove the guest (deleting the row) while the seat has zero ledger activity; the guest cannot control this row because they have no account |
| `public.khata_links` | Read-only, token-gated "living balance" page for one contact, shareable with someone who never installs Hisaab | `id`, `owner_id` (CASCADE), `person_id` (CASCADE from `persons`), `token_hash` (SHA-256, never client-readable), `initials_only`, `show_notes` (both default **false**), `expires_at` (default now()+90 days), `revoked_at`, `created_at` | **Owner only**, and even the owner cannot read `token_hash` (column grant excludes it) — RLS `owner_id = auth.uid()` on SELECT/UPDATE; INSERT/DELETE have no client policy at all (minting/revoking are RPC-only) | Links auto-expire after 90 days; revoked rows are **kept**, not deleted, so the lookup ledger keeps its FK and an operator can still see a link existed | `ON DELETE CASCADE` from both `auth.users` (owner) and `persons` (contact) — deleting the account or the contact removes the link | Owner can toggle `initials_only` / `show_notes` directly; revoke or rotate via `revoke_khata_link` / `create_khata_link` RPCs (rotating invalidates the previous link) |
| `public.khata_link_lookups` | Abuse-rate ledger (per-link hourly ceiling of 240, global miss circuit breaker at 500/15min) for the public khata endpoint | `link_id` (NULL = a miss), `looked_up_at` | **Nobody via the client** — no SELECT policy, no grant; only the `get_khata_view` definer function writes it | Rows older than the lookup window age out of relevance but there is no explicit prune function documented for this table (open item, see §9) | `link_id` follows the `khata_links` FK; specific `ON DELETE` behaviour for this join is set by the migration's FK clause | None — this table has no user-facing surface; it exists purely to rate-limit anonymous lookups. Per-IP rate limiting is explicitly **not possible** from SQL alone (`supabase-migration-p3-khata-link.sql` header, "RATE LIMITING") |
| `public.record_edits` | Append-only "who changed what" audit trail for money rows | `table_name`, `record_id`, `group_id` (nullable), `owner_id` (`SET NULL`), `actor_id` (`SET NULL`), `actor_kind` (`user`\|`system`), `action`, `changed` (JSONB `{column:{old,new}}`, whitelist only — **never a full row, never an account id in either app mode**), `created_at` | Owner of a personal row (`owner_id = auth.uid()`), or any **connected** member of the group for a group row (`is_group_member`) — the same visibility as the row it describes, never more | **180-day prune** (`prune_record_edits`, bounded 20k rows/call, scheduled `hisaab-prune-record-edits` at 03:41 UTC where `pg_cron` exists) — deliberately ≥ the 90/180-day notification retention so a notification a member still holds always still has its history behind it | `owner_id`/`actor_id` are `ON DELETE SET NULL` — a deleted user's past edits survive with `actor_id = NULL` but **stay `actor_kind = 'user'`** (not relabeled `'system'`, which is reserved for genuine no-JWT server paths), so "a person edited this and later deleted their account" stays distinguishable from a true system action; `group_id ON DELETE CASCADE` — a group's history dies with the group | Read-only via `EditHistorySheet` on the loan detail page, the group detail page and the group-expense editor (`src/pages/LoanDetailPage.tsx`, `GroupDetailPage.tsx`, `EditGroupExpenseModal.tsx`); no client can write, mute, or delete a row |
| `public.notification_prefs` | Per-user (optionally per-group) mute + quiet-hours + timezone | `user_id` (CASCADE), `group_id` (nullable, CASCADE from `split_groups`), `muted`, `quiet_hours_start`/`_end` (local hour 0-23), `tz` (IANA zone, default `Asia/Karachi`), `created_at`, `updated_at` | **Self only**, all four verbs (`user_id = auth.uid()`); the "is X muted" / "is it quiet hours for X" oracle functions are revoked from every client role, including the row owner's own session, mirroring the block model | No pruning function defined; a preference row persists until the user changes or the account is deleted | `ON DELETE CASCADE` from `auth.users` — removed outright with the account | Quiet-hours pickers in Settings (`src/pages/SettingsPage.tsx`, M5) and a per-group Mute/Unmute action in the group menu (`src/pages/GroupDetailPage.tsx`, `setGroupMuted`) |

## 2. Local Device Storage

### localStorage

Observed keys include:

- `hisaab_supabase_uid`: cached current Supabase user id for DB helper calls.
- `hisaab_user_name`: cached profile/display name.
- `hisaab_primary_currency`: cached primary currency.
- `hisaab_onboarded`: onboarding completion flag.
- `hisaab_data_version`: local app data version.
- `hisaab_pending_invite`: invite token captured before login.
- `hisaab_app_mode`: `splits_only` or `full_tracker`.
- `hisaab_lang`: UI language.
- `hisaab_pin_hash`: local PIN record — PBKDF2-SHA256 (150k iterations) with a random per-device salt as of the 2026-09-02 hardening (`src/lib/pinCrypto.ts`); a legacy single-round unsalted-SHA-256 record verifies once and is transparently upgraded.
- `hisaab_pin_lockout`: persisted failed-attempt count / lockout expiry for the PIN gate (added 2026-09-02, replaces the old in-memory-only counter that a refresh used to reset).
- `hisaab_identifier`: local PIN/account identifier.
- `hisaab_mobile`: mobile number typed into the Settings profile card — local-only (the cloud-synced, discoverable number is `profiles.phone_e164`, §1).
- `hisaab_push_token`: mirror of the FCM registration token so sign-out can delete the `device_push_tokens` row even after an app restart (`src/lib/pushRegistration.ts`).
- `hisaab_telemetry_consent`: the analytics consent choice (`granted`/`denied`, default denied) — inert in this build because no PostHog key ships.
- `hisaab_theme`: light/dark appearance (device-scoped).
- Assorted UX state: `hisaab_qe_last_source`/`_dest`, `hisaab_settlement_snoozes_v1`, `hisaab_khata_nudge_snoozed_until:*`, `hisaab_notif_prompt_dismissed_at`, `hisaab_payment_reminders_enabled`, `hisaab_daily_quote_enabled`, `hisaab_flex_income`, `hisaab_net_snapshots`, `hisaab_feedback_draft`, `hisaab_updates`, and similar.
- `hisaab_backfill_persons_v1`, `hisaab_backfill_persons_v1:lock`: migration flags.

Sign-out cleanup (`resetAllUserStores()`, `src/stores/resetAllStores.ts`) sweeps **every** `hisaab_`/`hisaab:`-prefixed key except the device-scoped keep-list `DEVICE_SCOPED_LOCALSTORAGE_KEYS` = {`hisaab_lang`, `hisaab_theme`, `hisaab_pwa_dismissed`} — so `hisaab_mobile`, `hisaab_push_token`, `hisaab_telemetry_consent` and `hisaab_supabase_uid` are all cleared. Supabase's own `sb-*` session keys are purged by `clearLocalAuthSession()`.

### sessionStorage

- `hisaab_pwa_dismissed`: dismisses the PWA install prompt for the current browser session.

### IndexedDB / Dexie

The app keeps one Dexie database **per user**, named `HisaabDB:user:<uid>` (`src/db/database.ts`), with tables for accounts, transactions, loans, EMI schedules, goals, activity logs, upcoming expenses, split groups, group expenses, group settlements, and persons. It is a **read mirror only** — Supabase is the source of truth; there is **no offline write queue** (the inert outbox scaffold was deleted 2026-09-04, decision D5, `docs/offline-story.md`), so an internet connection is needed to save entries. The database is deleted at sign-out and at account deletion (`Dexie.delete(databaseName)`, awaited by `resetAllUserStores()`). It is stored unencrypted inside the Android app sandbox — disclose "not encrypted at rest on device" honestly.

### Browser/Supabase Auth Storage

Supabase JS manages session persistence in browser storage by default. This includes session data such as access/refresh tokens required to keep the user logged in. The app also mirrors the current user id into `localStorage.hisaab_supabase_uid`.

## 3. Cloud Storage / Backend

Hisaab stores core app data in Supabase:

- Auth and email identity are handled by Supabase Auth.
- User profile and app preferences are stored in `profiles`.
- Personal finance records are stored in `accounts`, `transactions`, `loans`, `emi_schedules`, `goals`, `upcoming_expenses`, and `activities`.
- Contacts are stored in `persons`.
- Shared group data is stored in `split_groups`, `group_members`, `group_expenses`, `group_settlements`, `group_invites`, `group_events`, and `notifications`.
- Linked request workflows are stored in `linked_transaction_requests` and `linked_settlement_requests`.
- Receipt photos/PDFs are stored in the private `receipts` Storage bucket (`src/lib/receiptStorage.ts`; see §1).
- Investment records are stored in `investment_markets`, `investment_trades`, `investment_prices`; kameti (committee) records in `committees`, `committee_members`, `committee_payments`; budgets and recurring templates in `budgets`, `recurring_transactions`; user-defined categories in `custom_categories`.
- The user's own opt-in discoverable phone number lives on `profiles.phone_e164` / `profiles.phone_discoverable`; FCM push tokens in `device_push_tokens` (§1).
- Trust & safety records are stored in `public.blocks` and `public.reports`. Guest (no-account) group members' hashed phone identities are stored in `public.group_guest_identities`. Public khata-link capability URLs are stored in `public.khata_links` (+ the abuse-rate ledger `public.khata_link_lookups`). Per-record edit history is stored in `public.record_edits`. Notification fatigue preferences are stored in `public.notification_prefs`. All applied to production 2026-09-03/04. Full detail: §1a.

Cloud storage is required for account sync, shared groups, linked user workflows, notifications, push delivery, invite acceptance, receipt attachments, trust & safety enforcement, and account deletion/anonymization. Writes need a connection — nothing is queued offline.

## 4. Data Shared Between Users

Hisaab has collaboration features. In shared contexts, data visible to other users can include:

- Group name, currency, emoji, and members.
- Member display names, roles, connected/invited status, and joined state.
- Group expenses: description, amount, payer, splits, category, date, notes.
- Group settlements: payer/receiver members, amount, date, note.
- Group events: summaries of adds, edits, deletes, joins, and settlements.
- Group notifications targeted to connected members.
- Invite acceptance state and invite metadata, depending on group visibility.
- Linked transaction/settlement requests between two users, including amount, currency, note, status, and mirrored ledger ids.
- **(Added 2026-09-02)** Guest (no-account) group members: a display name and, for other connected members of the same group, their status as a "guest" — never the guest's raw phone number, which exists only as an unreadable hash (§1a).
- **(Added 2026-09-02)** Edit history: for a group expense or settlement, any **connected** member of that group can see a structured before/after diff (money, date, note, splits, participants) of who changed what, attributed by name or "someone/system" (§1a).
- **(Added 2026-09-02)** A khata link is deliberately shareable **outside** the app: whoever holds the URL sees one contact's name, per-currency balance, and loan/repayment history (notes only if the owner opted in, capped at 140 chars) — no login, no way to distinguish the intended recipient from anyone the link was forwarded to. Kameti witness links (`/kameti/witness/TOKEN`, expiring) likewise show a draw result to whoever holds the URL. These are the flows in this section where the recipient need not be a Hisaab user at all (§1a).
- **(Added 2026-09-05)** Phone discovery, only while the user has switched it ON (default OFF): another Hisaab user who has *already saved that number* as a contact is told it belongs to a Hisaab account (display name + public code) and can send a link request. No number is ever revealed in the other direction, and the device address book is never read (`src/components/PhoneDiscoverySection.tsx`, `supabase-migration-connections-push-discovery.sql` §4).

Private personal accounts, private transactions, private goals, private upcoming expenses, private contacts, blocks, reports, and notification preferences are not intended to be visible to other users except where the user explicitly initiates linked/group/khata-link workflows or exports/shares backup data. Blocks and reports are additionally never visible even to the person they are about — see §1a.

## 5. Data Not Collected

Based on current code inspection, Hisaab does not appear to collect or request:

- GPS or precise location.
- Address book/native device contacts.
- Microphone/audio.
- SMS or phone call logs.
- Health or fitness data.
- Advertising ID.
- Biometric data.
- Installed apps.
- Web browsing history.

**Camera/photos are collected (corrected 2026-09-02, permission confirmed 2026-09-05).** The Android manifest **does** declare `android.permission.CAMERA` (with `<uses-feature android:required="false">`, so camera-less devices still install — `android/app/src/main/AndroidManifest.xml`). Two features use it: the in-app QR scanner for connecting two users face to face (`getUserMedia` in `src/components/QRScanner.tsx`; frames are decoded on-device and never uploaded), and the receipt field, whose file input carries `capture="environment"` so Android opens the camera directly (`src/components/ReceiptField.tsx`; gallery/file picker is the alternative). Receipt photos/PDFs go to a private Supabase Storage bucket (`receipts`) keyed under the owner's uid (`src/lib/receiptStorage.ts`); `supabase-migration-p2-trust-safety.sql` §8 enforces a 5 MiB size cap and a `image/jpeg` | `image/png` | `image/webp` | `application/pdf` MIME allowlist. See the "Receipt photos / PDFs" row in §1 above and disclose as **Photos** + **Files and docs**. The app uses clipboard write operations for invite links/user codes/group codes/khata-link URLs. It uses file input for JSON backup import and receipt selection, and browser download APIs for backup export. The only other declared permissions are `INTERNET` and `POST_NOTIFICATIONS` (merged from `@capacitor/local-notifications`; covers FCM too).

## 6. Security / Privacy Controls

- Authentication is via Supabase Auth email/password. Password policy: at least 8 characters with at least one letter and one digit (`src/lib/passwordPolicy.ts`). Change-password and delete-account both re-ask the current password (`verifyCurrentPassword`, `src/pages/SettingsPage.tsx`).
- Supabase Row Level Security is present in schema/migrations for user-owned tables and shared group visibility.
- Permanent account deletion is implemented through `delete_current_user` (`supabase-migration-p0-launch-blockers.sql` → `audit-p0-account-deletion` → `p3-account-deletion-balance-gate`, all applied). In-app: Settings → Delete account → type `DELETE` + current password. It deletes the Supabase Auth identity; foreign-key cascades remove personal records, receipts, push tokens, blocks, khata links, notification prefs and solo groups, while `ON DELETE SET NULL` references (shared-group ledger rows, reports, edit history) are anonymized. **The RPC refuses (founder decision D1, live in production)** with `OWNED_GROUPS_WITH_MEMBERS` while the caller owns a shared group that still has other members (transfer ownership or archive first) and with `UNSETTLED_GROUP_BALANCES` while the caller owes or is owed in a shared group that still has another member (settle first — the same rule as leaving a group). Both refusals are surfaced in-app with the group names/amounts and are described on `/delete-account`.
- Deleted users are blocked on login/session restore by checking `profiles.is_deleted`.
- Logout clears in-memory Zustand stores and most user-scoped localStorage keys.
- Local PIN is a local device app lock, and — corrected 2026-09-02 — it is now actually enforced: `src/App.tsx`'s "Device PIN gate" (audit H7 / QA F-1 fix) renders `PinLockScreen` as the last gate before the app shell (after auth, email verification and onboarding), on cold start whenever a PIN record exists and again after the app has been backgrounded ≥60s (`PIN_RELOCK_AFTER_MS`, `src/lib/pinCrypto.ts`). This closes the gap `docs/audit-2026-09/12-qa-review.md` F-1 originally flagged (zero importers of `PinLockScreen`). The hashing scheme was hardened in the same pass — v2 records use PBKDF2-SHA256 at 150,000 iterations with a random per-device 16-byte salt, replacing the old single-round unsalted-SHA-256-with-a-hardcoded-string scheme; a v1 record still verifies once and is transparently upgraded to v2 on the owner's next successful unlock. A persisted, exponentially-doubling lockout (5 free attempts, then 30s doubling to a 15-minute cap, `PIN_LOCKOUT_KEY`) survives an app kill, unlike the old in-memory-only counter. It remains a **local device gate**, stored in localStorage rather than a native secure-enclave/keystore secret — do not claim hardware-backed protection.
- Backup export produces a JSON file containing sensitive financial and settings data. After export, the user controls where that file is stored/shared.
- Backup import deletes and recreates user-owned cloud records for several tables. This is high-impact and currently guarded by a browser confirmation.
- Service worker/PWA caching exists and should be reviewed before native packaging to avoid stale cached shells.

## 8. Privacy Policy Draft Points

Include:

- App name: Hisaab 2.0 / Hisaab.
- Developer/legal entity and privacy contact email.
- What account data is collected: email, name, user id, public code, preferences.
- What financial data is collected: accounts, balances, transactions, loans, EMI schedules, settlements, goals, budgets, recurring entries, upcoming expenses, investment records, kameti (committee) rounds and payments — in any currency.
- What collaboration data is shared with other users in groups and linked requests, including guest (no-account) members; and that with the opt-in "discoverable by phone" toggle ON (default OFF), people who already have the user's number saved can find their account.
- Camera use: the QR scanner for connecting two users (frames stay on-device) and receipt photos (uploaded only when the user attaches one, private bucket, deleted with the transaction/account).
- What local data is stored on device, including the local PIN record (an enforced device lock, not just a stored hash — §6), cached settings, and the unencrypted per-user IndexedDB read mirror.
- What cloud provider is used: Supabase for auth/database/realtime/storage; Vercel for hosting.
- That writes need an internet connection — nothing is queued offline.
- How backup export/import works and that exported JSON files may contain sensitive financial data.
- Account deletion policy: in-app (Settings → Delete account, type `DELETE` + current password) or via `/delete-account`; that deletion is **refused** while the user owns a shared group with other members (transfer ownership / archive first) or owes / is owed in a shared group with another member (settle first); permanent Auth identity deletion, personal-record cascades, and anonymization or removal of shared references where applicable — reports and edit-history rows survive with the deleted user's id nulled (never fully erased, so an operator's abuse record and a group's dispute trail are not lost to a self-deletion); blocks, khata links, notification preferences and push tokens are deleted outright; receipt photos are purged from the storage index (a logical purge — see the residual risk in §9) at deletion time.
- User-initiated public sharing: that a user can mint a read-only "khata link" exposing one contact's balance to anyone holding the URL, with no login on the other end, notes off by default, an initials-only option, a 90-day expiry, and owner-controlled revoke/rotate.
- Trust & safety: that users can block (silently, one-sided) and report each other, that reports are reviewed by the operator and survive the reporter's or reported user's account deletion, and the residual limitation that blocking is per-account (a deleted-and-re-registered harasser gets a clean slate until phone verification exists).
- Data retention policy for private records, shared group records, deleted profiles, backups, notifications (90 days read / 180 unread), and edit history (180 days).
- Security measures: authentication, RLS, HTTPS/cloud provider controls, logout clearing, and the hardened local PIN scheme (PBKDF2-SHA256, 150k iterations, random per-device salt, persisted lockout — §6).
- User rights/contact method for data access, correction, deletion, and support.
- Whether data is sold/shared for advertising: current code shows no ad SDK or advertising ID.
- Product analytics: described as "**if enabled in a release and you agree**" — off by default, a Settings toggle, PostHog (EU) as the processor, exactly which categories would be sent (never amounts, names, phone numbers or note text), and how to turn it off again. The 1.0.0 build ships no analytics at all.
- Push notifications: that Google/Firebase Cloud Messaging is the delivery processor for background/killed-app push (live), that a device token is stored only after the user turns notifications on, and that it is removed on sign-out, opt-out and account deletion — see §7's third-party list.
- Crash reporting: that Sentry (EU) receives crash logs and diagnostics from the release build, without names, amounts or user ids.
- International transfer/storage note if Supabase region is outside user country.
- Effective date and update process.
