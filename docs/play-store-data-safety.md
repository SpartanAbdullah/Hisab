# Hisaab Play Store Data Safety Notes

Last reviewed: September 2, 2026 (trust & safety, khata link, edit history, guest members, notification prefs additions)

This is an internal developer note for preparing the Google Play Console Data Safety form. It is based on the current Hisaab codebase and must be checked against the final production environment, Supabase project settings, Vercel settings, and the Android release build before submission.

## Product Scope

Hisaab is a personal finance record-keeping app. It is not a bank, wallet custody provider, lender, money transfer provider, investment platform, or financial adviser.

## Data NOT Collected For a Feature That Is Only Planned

`docs/phone-auth.md` is a **proposal only — nothing implemented, no SQL run against production**. Do not disclose OTP-based phone verification, a `phone_verified_at` column, or any related identity-linking flow in the Data Safety form until that migration actually ships. The *existing* self-service `persons.phone` / contact-discovery phone flows (already disclosed above) are unrelated and unaffected by this note.

## Sharing

- Hisaab does not include advertising SDKs and the codebase does not show sale of user data.
- Supabase processes authentication and cloud data storage on Hisaab's behalf, including the new trust & safety, khata-link, edit-history, guest-identity, and notification-preference tables above.
- Vercel processes hosting and delivery traffic needed to serve the web app.
- PostHog (PostHog Inc., **EU Cloud / Frankfurt**) processes opt-in product analytics. **Nothing is sent unless the user explicitly enables it** — consent is device-level, defaults to OFF, and gates every `track()` call. When enabled it receives: event names from a fixed catalog, enum/boolean/integer/bucket properties, and the user's Supabase auth UUID as the distinct id. It never receives amounts, balances, names, phone numbers, notes, account/group/kameti names, free text, or URLs (URL and referrer properties are on the SDK's `property_denylist`). `$ip` collection is off; autocapture, session recording, surveys and web experiments are off.
- Sentry (Sentry GmbH, EU region) processes crash and diagnostic information. **This build has `VITE_SENTRY_DSN` configured, so crash data IS collected and shared with Sentry.** `sendDefaultPii: false`; no user ID is attached at any current call site (keep it that way or re-disclose).
- **Google (Firebase Cloud Messaging)** — implemented but **believed not yet configured in production** (`docs/notifications.md` §1, N-4). Once live, a device's push registration token and the composed notification title/body/deep-link path are sent to Google's FCM service so it can deliver to a killed/backgrounded app. No account/financial data beyond what the notification text itself names (e.g. "Ali added an expense") is sent to Google. Confirm `app_push_config` state in production before declaring this live in the Data Safety form; if it is genuinely still unconfigured, this row is inert and can be marked "collected, not currently shared" with a note to re-check before each release.
- Users intentionally share limited records with other Hisaab users when they use groups, invites, linked loan requests, linked settlement requests, or group guest seats.
- **A user can share a read-only "khata link" with anyone holding the URL — not a Hisaab account holder, and not a Hisaab third-party processor.** This is user-initiated sharing of a strict, capped projection of one contact's balance (never a phone/email/account id; notes only if the owner opts in, capped at 140 characters). The owner controls minting, revoking, and rotating it at any time. `supabase-migration-p3-khata-link.sql`.
- User-exported JSON backups leave the app only when the user downloads and shares them.

Confirm in Play Console whether service-provider processing should be described as "shared" under the current Google Play definitions and exceptions.

## Deletion

Users can start deletion in the app:

1. Sign in.
2. Open Settings.
3. Open **Delete account**.
4. Type `DELETE` and confirm.

The client calls the Supabase `delete_current_user` RPC, signs out, clears user stores, clears user-scoped local storage keys, and awaits deletion of the user's IndexedDB database. After `supabase-migration-p0-launch-blockers.sql` is applied, the RPC permanently deletes the matching `auth.users` identity. Existing foreign keys cascade personal money tables and owned groups; shared references configured with `ON DELETE SET NULL` are anonymized.

**What survives account deletion, and how it is anonymized (added 2026-09-02):**

- **Shared-group ledger rows** (`group_expenses`, `group_settlements`, `group_events`) a deleted user authored inside a group they shared with others survive for the remaining members, per the existing account-deletion migration's group handling — the ledger a group depends on is not erased by one member leaving it.
- **Reports about, or filed by, the deleted user** (`public.reports`) survive with `reporter_id` and/or `reported_id` set to `NULL` (`ON DELETE SET NULL`, not CASCADE) — deliberately, so a reported user cannot erase the operator's only record by deleting their account. Validated end to end: `docs/trust-and-safety.md` §3.
- **Edit-history rows the deleted user authored** (`public.record_edits`) survive with `actor_id` set to `NULL` (`ON DELETE SET NULL`). They are **not** relabeled to `actor_kind = 'system'` — that value is reserved for rows written by a genuine server-side path with no signed-in user (cron, service role, the push function) — so a deleted user's past edits remain distinguishable as "a person did this and later deleted their account" (`actor_kind` stays `'user'`, `actor_id` is `NULL`) versus a true system action. `supabase-migration-p2-edit-history.sql` (column comment on `actor_kind`), `docs/edit-history.md` §2, §4.
- **Blocks, khata links, and notification preferences the deleted user owned are removed, not anonymized** — `blocks.blocker_id`/`blocked_id`, `khata_links.owner_id`, and `notification_prefs.user_id` are all `ON DELETE CASCADE` against `auth.users`, so these rows are deleted outright with the account.
- **Receipt photos** — `delete_current_user()` now deletes the caller's `receipts/<uid>/` rows from `storage.objects` before removing the Auth identity (`supabase-migration-p2-trust-safety.sql` §8.3). **This is a logical purge, not a guaranteed physical one**: deleting the `storage.objects` index row makes the file unreachable through the API (no signed URL, no list result), but does not itself issue a delete against the underlying object storage blob. A full physical purge still needs a storage-API removal with the service-role key. Do not represent account deletion as an immediate physical erasure of receipt image bytes in the privacy policy — `docs/trust-and-safety.md` §6.1.

A stale JWT cannot recreate rows because the Auth identity no longer exists and restrictive active-profile RLS policies reject the deleted user.

The public deletion instructions are available at `https://usehisaab.com/delete-account`. Users can also email `support@usehisaab.com`.

## SDK and Permission Review

Current code review found:

- **Analytics:** `posthog-js` (pinned, EU Cloud) is present as of 2026-09-02. It is **opt-in and default-off**, and is inert with no `VITE_POSTHOG_KEY` (the SDK is behind a dynamic import, so it is not even downloaded). Before submitting, check whether the release build sets the key: if it does, declare "App activity → App interactions" and "User IDs" as **collected and shared with a third party, optional, for Analytics**; if it does not, analytics is genuinely absent from that build. Note `src/lib/analytics.ts` is NOT telemetry — it is the user's own spending aggregation for in-app charts and sends nothing anywhere.
- **Ads:** no advertising SDK found.
- **Crash reporting:** Sentry integration is **enabled** (`VITE_SENTRY_DSN` configured). Crash/diagnostic data is collected and shared with Sentry GmbH (EU). `sendDefaultPii: false`; no user ID attached at current call sites.
- **Push notifications:** the FCM tier-3 delivery path (`push-notify` edge function → Google FCM) is **implemented** as of the notification-maturity work but **believed unconfigured in production** (`docs/notifications.md` §1, N-4) — confirm `app_push_config` state before declaring it live. The app also has database-backed in-app notifications and device-local scheduled reminders that never leave the device.
- **Device identifiers:** no dedicated device identifier SDK found. PostHog is configured with `ip: false` and no device-ID capture of any kind (`src/lib/telemetry.ts`).
- **Location:** no location or geolocation SDK usage found. The IANA **timezone string** stored in `notification_prefs.tz` (e.g. `Asia/Karachi`) is a coarse UTC-offset label used only to schedule quiet hours, not device geolocation — do not conflate it with a location permission in the form.
- **Contacts:** no native address-book permission or contacts SDK found. Users may manually enter contact names and phone numbers, including guest group members (phone stored only as a SHA-256 hash, unreadable by any client role — see the table above).
- **Camera/photos:** no camera *permission* is requested (uploads use a file picker), but the app **does** support attaching receipt photos/PDFs to a transaction, stored in a private Storage bucket with a 5 MiB / MIME-allowlist cap as of 2026-09-02 — disclose as Photos/Files under Data Safety; see the "Receipt photos" row above.
- **Files:** JSON backup export and import exist. Import reads a user-selected `.json` file locally; no arbitrary upload feature beyond receipt attachments was found.
- **Clipboard:** invite URLs, khata-link URLs, and share text can be copied when the user requests it.
- **Payments:** no payment SDK found.
